What attestation establishes
Two verified boundaries.
The client verifies the CPU service before sending a plan, token or text. The CPU service independently verifies the inference enclave before transmitting text to it.
Hardware evidence→Release measurement→Approved deployment→TLS peer key
Tinfoil verification checks the code/release evidence, enclave evidence and matching measurements. The caller pins an independently approved repository and release digest. The attested TLS key authenticates the encrypted connection.
The CPU’s measured launch configuration pins the executor image and trust configuration. The client additionally checks the manifest’s policy digest. The executor checks the plan’s approved model release and its reviewed mapping to a modelwrap artifact root.
How the report key becomes trusted
The client fetches /aiab/pubkey over the verified CPU connection. That response identifies the boot and report key. The report key is distinct from the TLS key; it is not itself a portable hardware quote.
Recorded boot identity
The offline verification tooling uses a separately pinned identity anchor and a saved report bundle. Later offline signature verification needs that independently trusted saved key/identity anchor. An untrusted file claiming “attestation passed” cannot establish that anchor. This page displays recorded evidence; it does not contact the service or revalidate hardware attestation.

What this run does not prove
  • That the classifier is correct under adversarial inputs. Three synthetic cases are a smoke test, not an accuracy study.
  • That the logger captured all events or verified a native WORM/Rekor checkpoint.
  • That two independent organizations approved this demo: both role keys were provisioned locally for testing.
  • That a boolean result limits total disclosure to one bit. Metadata, failures, timing and repeated runs remain observable.
  • That the historical deployment is still running with this boot key. Restart rotates its key and loses in-memory state.
